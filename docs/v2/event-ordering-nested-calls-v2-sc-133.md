# V2-SC-133 — Event ordering across nested module calls

## Authoritative rule

For one successful EVM transaction, canonical observation order is
`(blockNumber, transactionIndex, logIndex)`. A caller emits its `entered` event
before invoking a downstream module. The downstream subtree is contiguous, and
the caller emits `completed` only after the downstream call succeeds. Thus a
six-module call is a properly nested sequence:

`governance enter → claims enter → custody enter → settlement enter → rewards enter → treasury enter → treasury complete → rewards complete → settlement complete → custody complete → claims complete → governance complete`.

Every event in the operation carries the same non-zero `bytes32 correlationId`
and claim identifier. Correlation IDs are opaque, transaction-scoped protocol
identifiers; consumers must not derive authority from them. A successful ID is
consumed once. A revert at any depth removes all logs and state changes, so a
retry uses the same ID only when the first transaction reverted. Across
transactions, consumers use canonical chain ordering and the reorg policy in
`docs/reorg-consumer-guarantees.md`.

## Assurance boundary

`CrossModuleEventOrderingFixture.sol` is under `contracts/mocks` and is never a
deployable canonical module. It neither imports nor calls production modules,
holds assets, grants roles, nor gains settlement/treasury authority. It exists
only to test the EVM nesting and correlation contract shared by claims, custody,
settlement, rewards, treasury, and timelocked governance event consumers.

No production interface, storage layout, role, configuration version,
deployment manifest, ABI freeze, or released artifact changes in this issue.
V2-SC-003 frozen active-claim parameters and V2-SC-131 versioned ABI exports
therefore remain compatible. Active claims require no migration.

## Failure modes and invariants

- zero correlation IDs fail before mutation;
- only the configured upstream may enter each nested boundary;
- only the configured timelock may begin the operation;
- replay of a successfully consumed ID fails closed;
- a downstream failure atomically rolls back the consumed marker, reconciliation
  record, and all logs;
- the path has a fixed six-module depth and twelve logs, with no data-dependent
  loops, token transfer, rounding, or external user-selected call target;
- storage reconciliation requires `consumed[id] == true` and
  `reconciledClaim[id] == claimId` after success.

## Evidence and residual risk

`test/v2/V2SC133EventOrdering.t.sol` covers success, exact ordering, correlation,
zero-ID boundary behavior, authorization, replay, nested failure rollback, and
fuzzed claim/identifier values. ABI drift remains covered by the V2-SC-131
export gate because this change adds no canonical ABI.

Residual risk is limited to integration code that emits canonical production
events: the fixture proves the ordering contract and EVM atomicity, but does not
invent a production mega-transaction where none exists. Exact-head maintainer
approval remains a release-process requirement and cannot be self-attested by
the test suite.
